## 1. 项目背景与目标

### 1.1 项目背景
传统的企业内部知识传递依赖翻阅大量文档（如《用户手册》、《规章制度》、《技术文档》），效率低下。通用大模型（如ChatGPT）虽然强大，但无法针对企业私有数据进行回答，且存在“幻觉”风险。同时，不同企业之间的数据必须严格隔离，以满足合规与安全要求。

### 1.2 项目目标
构建一个**基于RAG（检索增强生成）架构的 SaaS 化企业级智能知识库问答平台**。
- 允许**每个租户（企业/组织）** 独立上传和管理自己的私有文档。
- 各租户的向量数据库、文件存储、对话历史**完全隔离**。
- AI仅根据当前租户上传的文档内容作答，确保答案的准确性、可追溯性及数据隐私性。
- 平台通过统一的登录入口，根据租户标识（如子域名或请求头）自动路由到对应租户的数据空间。

## 2. 用户角色定义与权限矩阵

### 2.1 三种角色定义

| 角色名称 | 系统定义 | 核心职责 |
| :--- | :--- | :--- |
| **平台超级管理员（Super Admin）** | 平台级 | 管理所有租户（创建、禁用、删除），配置全平台默认AI模型，查看全局系统运行状态与总账单。 |
| **租户管理员（Tenant Admin）** | 租户级（每个企业1~N个） | 管理本企业的知识库（上传/删除文件）、管理本企业成员、配置本企业的AI模型（可选）、查看本企业数据看板与消耗统计。 |
| **普通用户（User）** | 租户级（每个企业N个） | 仅能在本企业授权的知识库范围内进行提问、查看对话历史与引用来源。 |

### 2.2 权限矩阵（菜单与操作可见性）

| 功能模块 | 具体操作 | 平台管理员 | 租户管理员 | 普通用户 |
| :--- | :--- | :--- | :--- | :--- |
| **租户管理** | 创建/禁用/删除租户 | ✅ | ❌ | ❌ |
| **成员管理** | 邀请/移除本企业成员，分配角色（管理员/普通用户） | ❌ | ✅ | ❌ |
| **知识库管理** | 上传/删除/替换文件 | ❌ | ✅ | ❌ |
| **知识库管理** | 浏览文件列表、查看解析状态 | ❌ | ✅ | ✅（仅查看） |
| **智能问答** | 发起提问、查看流式回答 | ❌ | ✅ | ✅ |
| **智能问答** | 查看引用溯源（来源文件/章节） | ❌ | ✅ | ✅ |
| **AI模型配置** | 配置本企业专属 API Key / Base URL（BYOK） | ❌ | ✅ | ❌ |
| **数据看板** | 查看本企业的文档数、问答趋势、Token消耗 | ❌ | ✅ | ❌ |
| **系统监控** | 查看全局日志、所有租户资源占用、平台收入 | ✅ | ❌ | ❌ |
| **全局模型配置** | 设置平台默认的AI模型及API密钥（作为备选/默认值） | ✅ | ❌ | ❌ |

### 2.3 权限校验规则

系统需在每次API请求时进行权限校验，核心规则如下：

1. **身份认证**：用户登录后获取 JWT 令牌，令牌中包含 `user_id`、`tenant_id`、`role` 三个关键字段。后续所有请求必须携带该令牌。

2. **租户访问控制**：
   - 平台管理员可访问所有租户的数据，不受租户隔离限制。
   - 租户级用户（管理员和普通用户）仅能访问其所属租户的数据。系统需从请求中提取租户标识（如子域名或 `X-Tenant-ID` 请求头），并与令牌中的 `tenant_id` 进行比对，若不一致则拒绝访问。

3. **操作权限控制**：
   - 租户管理员可执行知识库管理、成员管理、模型配置、查看看板等操作。
   - 普通用户仅可执行智能问答和查看引用溯源，无权访问任何管理类功能。
   - 平台管理员不可操作具体租户内的文件或问答，仅负责平台层面的租户管理和系统监控。

## 3. 核心功能需求

### 3.1 租户管理（仅平台管理员）
- **创建租户**：填写企业名称、企业管理员账号（邮箱）、子域名（如 `company-a.intellikb.com`），系统自动生成唯一的 `tenant_id`。
- **禁用/启用租户**：暂停某个租户的全部服务，保留数据，恢复后可继续使用。
- **删除租户**：物理删除该租户所有数据（包括向量库、文件、对话记录、成员），需二次确认，且建议设置7天数据导出缓冲期。

### 3.2 知识库管理（租户管理员，作用于当前租户）
系统应为每个租户提供独立的知识库管理后台。

- **3.2.1 文件上传**：支持批量上传多种格式文件，包括 `.doc`, `.docx`, `.pdf`, `.txt`, `.md`。所有文件归属当前租户，系统自动关联 `tenant_id`。

- **3.2.2 文件解析与存储**：
  - 原始文件保存至当前租户专用的对象存储路径（如 `/tenant-{tenant_id}/` 目录下）。
  - 后端异步抽取文件中的纯文本内容，进行切片和向量化，所有向量数据均包含 `tenant_id` 标签。

- **3.2.3 文件删除与替换**：
  - 支持删除文件，系统必须**物理删除**该租户下对应的向量数据和原始文件。
  - 支持覆盖上传（同名文件），系统自动执行“先删旧向量，后加新向量”的原子性操作，且操作范围限定在当前租户。

- **3.2.4 状态反馈**：文件上传/解析过程中，前端界面需实时显示处理进度（如“上传中”、“解析中”、“向量化中”、“已完成”），进度信息仅对当前租户可见。

### 3.3 AI 智能问答（租户内所有用户）
系统应提供类ChatGPT的流式对话界面，所有对话绑定当前租户。

- **3.3.1 流式输出（SSE）**：AI回答必须逐字（或逐词）推送到前端，降低用户等待焦虑。

- **3.3.2 检索增强生成（RAG）**：
  - 用户提问时，系统**仅检索当前租户的向量数据库**（通过 `tenant_id` 过滤），召回最相关的 Top-K 个文档切片（默认 K=5）。
  - 将检索到的内容作为“参考资料”拼接进提示词，要求大模型严格基于参考资料回答。

- **3.3.3 拒绝回答机制**：若当前租户向量库中无相关内容，或检索到的相关度分数低于系统阈值，应引导大模型回复：“抱歉，当前知识库中暂无相关内容，请上传相关文档后再提问。”

- **3.3.4 引用溯源**：每个回答下方需显示该答案引用了哪些源文件（如“来源：用户手册.doc 第3章节”），且该文件必须归属于当前租户，增强答案可信度。

### 3.4 数据可视化看板（租户管理员）
- 展示当前租户的总文档数、向量切片总数。
- 展示当前租户近7日问答趋势图、高频提问词云。
- 展示当前租户的平均响应延迟与Token消耗估算（便于成本控制）。

### 3.5 AI 模型接入配置（租户管理员，新增核心模块）
本平台支持**两种AI模型接入模式**，由租户管理员在后台自行选择：

- **3.5.1 默认模式（平台统一提供，开箱即用）**
  - 租户创建后自动生效，无需任何配置。
  - 使用平台超级管理员预先设置的全局默认模型（如 DeepSeek-V3 或 GPT-4o-mini）和平台统一采购的 API Key。
  - 所有问答请求走平台统一的模型网关，Token消耗由平台记录，便于向租户计费。

- **3.5.2 自定义模式（BYOK - Bring Your Own Key，高级企业定制）**
  - 租户管理员可在“模型配置”页面手动开启“自定义模型”开关。
  - 需填写的配置项包括：
    - **API Key**：企业自行向大模型厂商（OpenAI / 阿里云 / DeepSeek）申请的密钥。
    - **Base URL**（可选）：模型服务地址，默认为官方地址；可填写企业私有化部署的模型地址。
    - **模型名称**：如 `gpt-4o`、`qwen-max`、`deepseek-r1`。
  - 保存后，该租户的所有问答请求将**优先使用企业自己的密钥和模型**，不再消耗平台公共额度。
  - **安全要求**：企业填写的 API Key 在后端必须加密存储（如 AES-256），前端界面仅展示掩码（如 `sk-****1234`），不可明文显示。

- **3.5.3 模型路由规则**（业务规则）
  - 系统在处理每个租户的问答请求时，首先检查该租户是否已配置自定义模型。
  - 若已配置，则使用租户自己的 API Key、Base URL 和模型名称发起调用。
  - 若未配置，则回退到平台全局默认模型配置。
  - 该路由逻辑对普通用户完全透明，用户无需感知底层使用的是哪个模型。

- **3.5.4 权限控制**：该配置页面仅对“租户管理员”角色可见，普通用户无任何配置入口。

## 4. 知识库动态更新机制（多租户隔离版）

**核心原则**：所有更新操作均限定在当前租户上下文中，不同租户的数据完全隔离，互不可见。

| 用户操作（当前租户） | 后端处理逻辑 | 向量数据库状态 | 前端反馈 |
| :--- | :--- | :--- | :--- |
| **上传新文件** | 1. 保存文件至 `/tenant-{tenant_id}/` 路径。<br>2. 异步执行：抽取文本 → 切片 → 生成向量，所有数据写入 `tenant_id`。<br>3. 插入新向量至向量库。 | 当前租户新增向量，其他租户无影响 | 提示“文件 [名称] 已成功入库，可开始提问”。 |
| **删除已有文件** | 1. 根据 `file_id` + `tenant_id` 删除向量。<br>2. 删除对象存储中的原始物理文件。 | 当前租户移除对应向量 | 提示“文件已删除”。 |
| **覆盖同名文件** | 先执行旧文件的“删除逻辑”（限定 tenant_id），再执行新文件的“上传新增逻辑”，需在一个事务内完成，避免脏数据。 | 当前租户先删后增 | 提示“文件更新成功”。 |

> **异步处理要求**：为防止大文件解析导致接口超时，文件解析与向量化必须采用**异步任务队列**（如 Celery + Redis），并通过 WebSocket 向前端推送处理状态。

## 5. 非功能需求（质量属性）

### 5.1 性能要求
- **首字延迟**：开启流式输出后，用户提问到看到第一个字的时间 < 500ms。
- **并发支持**：平台总并发用户数 ≥ 500，单租户内并发 ≥ 50。
- **检索速度**：向量检索耗时 < 200ms（单租户百万级数据量下）。

### 5.2 安全与合规
- **多租户鉴权**：
  - 使用 JWT 进行身份认证，Token 中包含 `tenant_id` 和 `role`。
  - 每个 API 请求必须携带租户标识（通过**子域名**或 **X-Tenant-ID 请求头**），后端需校验当前用户是否有权访问该租户。
- **数据隔离**：
  - **逻辑隔离（强制）**：所有数据库表、向量集合、Redis 键、对象存储路径均包含 `tenant_id` 字段，查询时自动带租户过滤条件。
  - **物理隔离（可选）**：可为大型租户提供独立数据库实例或独立向量集合（如 Milvus 的 Partition Key）。
- **API Key 加密存储**：租户管理员配置的自定义 API Key，在数据库中必须加密存储（AES-256），前端仅展示掩码。

### 5.3 运维与部署
- **容器化**：全部服务（前端、后端、数据库、中间件）支持 Docker 一键启动（`docker-compose up`），默认包含一个演示租户。
- **高可用**：生产环境支持 Kubernetes（K8s）编排与滚动更新，各租户可通过 Ingress 路由区分子域名。
- **日志监控**：集成结构化日志输出，日志中标注 `tenant_id`，便于按租户追踪问题；接入 Prometheus + Grafana 监控体系。

## 6. 技术栈总览（多租户适配）

| 层级 | 技术选型 | 多租户适配说明 |
| :--- | :--- | :--- |
| **前端** | React + TypeScript + Tailwind CSS | 从登录页获取租户标识，并在所有请求 Header 中携带；根据角色动态渲染菜单 |
| **前端通信** | Axios (HTTP) + SSE (流式接收) + WebSocket (状态推送) | - |
| **后端框架** | Python 3.11 + FastAPI | 中间件解析租户标识并注入请求上下文；通过依赖注入实现角色权限校验 |
| **AI 框架** | LangChain / LlamaIndex | 检索器增加 `tenant_id` 过滤条件；模型调用层支持多租户路由 |
| **大模型** | 支持多模型（OpenAI GPT / 通义千问 / DeepSeek） | 通过适配层支持“平台默认Key”和“租户自定义Key”双模式切换 |
| **向量数据库** | PGVector（首选） / Milvus（备选） | PGVector 用 `tenant_id` 列过滤；Milvus 用 Partition Key 实现租户隔离 |
| **关系型数据库** | PostgreSQL | 所有表含 `tenant_id` 字段，可启用行级安全（RLS）策略 |
| **非关系型数据库** | MongoDB | 存储对话聊天记录，每个文档存储 `tenant_id`，按租户建立索引 |
| **缓存/消息队列** | Redis | 键名前缀加 `tenant_id:`；消息队列任务携带 `tenant_id` |
| **对象存储** | MinIO（开发） / 阿里云OSS（生产） | 路径前缀 `/tenant-{tenant_id}/`，实现租户级目录隔离 |
| **部署** | Docker / Docker-Compose / Kubernetes | Ingress 根据子域名路由到同一后端，或统一转发后由后端解析 |
| **反向代理** | Nginx | 可配置根据子域名转发，或统一转发后由后端识别 |
| **CI/CD** | GitLab CI / GitHub Actions | 自动化测试与部署流水线 |
