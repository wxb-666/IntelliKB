## 1. 项目背景与目标

### 1.1 项目背景
传统的企业内部知识传递依赖翻阅大量文档（如《用户手册》、《规章制度》、《技术文档》），效率低下。通用大模型（如ChatGPT）虽然强大，但无法针对企业私有数据进行回答，且存在“幻觉”风险。

### 1.2 项目目标
构建一个**基于RAG（检索增强生成）架构的企业级智能知识库问答平台**。该系统允许用户上传私有文档，通过AI技术将文档转化为“外挂大脑”，实现**开卷考试式的精准问答**——AI仅根据上传的文档内容作答，若文档中无依据，则明确拒绝回答，从而确保答案的准确性与可追溯性。

## 3. 核心功能需求

### 3.1 知识库管理（管理员核心操作）
系统应提供一个可视化的知识库管理后台。

- **3.1.1 文件上传**：支持批量上传多种格式文件，包括 `.doc`, `.docx`, `.pdf`, `.txt`, `.md`。
- **3.1.2 文件解析与存储**：
  - 原始文件完整保存至对象存储（MinIO / 阿里云OSS）。
  - 后端异步抽取文件中的纯文本内容。
- **3.1.3 文件删除与替换**：
  - 支持删除文件，系统必须**物理删除**关联的向量数据。
  - 支持覆盖上传（同名文件），系统自动执行“先删旧向量，后加新向量”的原子性操作。
- **3.1.4 状态反馈**：文件上传/解析过程中，前端界面需实时显示处理进度（如“解析中”、“向量化中”、“已完成”）。

### 3.2 AI 智能问答（核心交互）
系统应提供一个类ChatGPT的流式对话界面。

- **3.2.1 流式输出（SSE）**：AI生成的回答必须逐字（或逐词）推送到前端，降低用户等待焦虑。
- **3.2.2 检索增强生成（RAG）**：
  - 用户提问时，系统先检索向量数据库，召回最相关的 Top-K 个文档切片（默认 K=5）。
  - 将检索到的内容作为“参考资料”拼接进Prompt，要求大模型基于参考资料回答。
- **3.2.3 拒绝回答机制**：若向量数据库检索到的相关度分数低于阈值，或参考资料中确实不包含答案，系统应引导大模型回复：“抱歉，当前知识库中暂无相关内容，请上传相关文档后再提问。”
- **3.2.4 引用溯源**：每个回答下方需显示该答案引用了哪些源文件（如“来源：用户手册.doc 第3章节”），增强可信度。

### 3.3 数据可视化看板
- 展示总文档数、向量切片总数。
- 展示近7日问答趋势图、高频提问词云。
- 展示平均响应延迟与Token消耗估算（便于成本控制）。

## 4. 知识库动态更新机制（核心逻辑）

本项目最关键的机制：**知识库会严格根据用户上传/删除的文件进行实时、增量更新。**

| 用户操作 | 后端处理逻辑（同步/异步） | 向量数据库状态 | 前端反馈 |
| :--- | :--- | :--- | :--- |
| **上传新文件** | 1. 保存文件至OSS。<br>2. 启动异步任务：抽取文本 → 切片（Chunking） → 调用Embedding生成向量。<br>3. **插入**新向量至向量库（保留 `file_id` 元数据）。 | **新增**（原有数据保留） | 提示“文件 [名称] 已成功入库，可开始提问”。 |
| **删除已有文件** | 1. 根据 `file_id` 发起向量库删除指令。<br>2. 删除OSS中的原始物理文件。 | **移除**（删除所有属于该文件的切片） | 提示“文件已删除”。 |
| **覆盖同名文件** | 1. 执行旧文件的“删除逻辑”。<br>2. 执行新文件的“上传新增逻辑”。<br>（需在一个事务内完成，避免脏数据） | **先删后增** | 提示“文件更新成功”。 |

> **注意**：为防止大文件解析导致接口超时，文件解析与向量化采用**异步任务队列（Celery + Redis）**，通过 WebSocket 推送处理状态。

## 5. 非功能需求（质量属性）

### 5.1 性能要求
- **首字延迟**：开启流式输出后，用户提问到看到第一个字的时间 < 500ms。
- **并发支持**：系统需支持至少 50 个并发用户同时提问。
- **检索速度**：向量检索耗时 < 200ms（百万级数据量下）。

### 5.2 安全与合规
- **鉴权**：采用 JWT（JSON Web Token）进行接口鉴权，区分普通用户与管理员的菜单权限。
- **数据隔离**：暂不强制多租户，但需在数据库设计中预留 `tenant_id` 字段，便于未来扩展。

### 5.3 运维与部署
- **容器化**：全部服务（前端、后端、数据库、中间件）必须支持 Docker 一键启动（`docker-compose up`）。
- **高可用**：生产环境支持 Kubernetes（K8s）编排与滚动更新。
- **日志监控**：集成结构化日志输出，接入 Prometheus + Grafana 监控体系。

## 6. 技术栈总览（严格对齐职位要求）

| 层级 | 技术选型 | 版本/说明 |
| :--- | :--- | :--- |
| **前端** | React + TypeScript + Tailwind CSS | 18.x / 4.9.x |
| **前端通信** | Axios (HTTP) + SSE (流式接收) + WebSocket (状态推送) | - |
| **后端框架** | Python 3.11 + FastAPI | 异步高性能框架 |
| **AI 框架** | LangChain / LlamaIndex | 用于RAG流程编排 |
| **大模型** | 支持多模型适配（OpenAI GPT / 通义千问 / DeepSeek） | 通过统一适配层切换 |
| **向量数据库** | PGVector（优先） / Milvus（备选） | 与PostgreSQL共用，减少中间件依赖 |
| **关系型数据库** | PostgreSQL | 存储用户、文件元数据 |
| **非关系型数据库** | MongoDB | 存储对话聊天记录（JSON结构） |
| **缓存/消息队列** | Redis | 缓存热点问答 + Celery Broker |
| **对象存储** | MinIO（开发） / 阿里云OSS（生产） | 存储原始上传文件 |
| **部署** | Docker / Docker-Compose / Kubernetes | 容器化与编排 |
| **反向代理** | Nginx | 负载均衡、静态资源缓存 |
| **CI/CD** | GitLab CI / GitHub Actions | 自动化测试与部署流水线 |
