## 1. 项目背景与目标

### 1.1 项目背景
传统的企业内部知识传递依赖翻阅大量文档（如《用户手册》、《规章制度》、《技术文档》），效率低下。通用大模型（如ChatGPT）虽然强大，但无法针对企业私有数据进行回答，且存在“幻觉”风险。同时，不同企业之间的数据必须严格隔离，以满足合规与安全要求。

### 1.2 项目目标
构建一个**基于RAG（检索增强生成）架构的 SaaS 化企业级智能知识库问答平台**。
- 允许**每个租户（企业/组织）**独立上传和管理自己的私有文档。
- 各租户的向量数据库、文件存储、对话历史**完全隔离**。
- AI仅根据当前租户上传的文档内容作答，确保答案的准确性、可追溯性及数据隐私性。
- 平台通过统一的登录入口，根据租户标识（如子域名或请求头）自动路由到对应租户的数据空间。

## 2. 用户角色定义

| 角色 | 职责描述 |
| :--- | :--- |
| **平台超级管理员（Super Admin）** | 管理所有租户（创建、禁用、删除租户），查看全局系统运行状态，不参与具体租户的知识库操作。 |
| **租户管理员（Tenant Admin）** | 归属于某个具体租户，拥有该租户内的全部权限：管理成员、上传/删除/更新知识库文件、查看租户内数据看板。 |
| **普通用户（User）** | 归属于某个具体租户，仅能在该租户授权的知识库范围内进行提问、查看对话历史。 |

## 3. 核心功能需求

### 3.1 租户管理（平台超级管理员）
- **创建租户**：填写企业名称、管理员账号、子域名（如 `company-a.intellikb.com`）。
- **禁用/启用租户**：暂停某个租户的全部服务，保留数据。
- **删除租户**：物理删除该租户所有数据（包括向量库、文件、对话记录），需二次确认。

### 3.2 知识库管理（租户管理员，作用于当前租户）
系统应为每个租户提供独立的知识库管理后台。

- **3.2.1 文件上传**：支持批量上传多种格式文件，包括 `.doc`, `.docx`, `.pdf`, `.txt`, `.md`。所有文件归属当前租户。
- **3.2.2 文件解析与存储**：
  - 原始文件保存至当前租户专用的对象存储路径（如 `/tenant-{tenant_id}/...`）。
  - 后端异步抽取文本，并关联 `tenant_id` 标签。
- **3.2.3 文件删除与替换**：
  - 支持删除文件，系统必须**物理删除**该租户下的对应向量数据。
  - 支持覆盖上传（同名文件），系统自动执行“先删旧向量，后加新向量”的原子性操作，且限定在当前租户。
- **3.2.4 状态反馈**：文件上传/解析过程中，前端界面需实时显示处理进度，进度信息仅对当前租户可见。

### 3.3 AI 智能问答（租户内用户）
系统应提供类ChatGPT的流式对话界面，所有对话绑定当前租户。

- **3.3.1 流式输出（SSE）**：AI回答逐字推送。
- **3.3.2 检索增强生成（RAG）**：
  - 用户提问时，系统**仅检索当前租户的向量数据库**，召回 Top-K 个相关切片。
  - 将检索内容作为参考资料，要求大模型基于参考资料回答。
- **3.3.3 拒绝回答机制**：若当前租户向量库中无相关内容，引导模型回复“抱歉，当前知识库中暂无相关内容”。
- **3.3.4 引用溯源**：显示答案来源的具体文件及章节，且该文件属于当前租户。

### 3.4 数据可视化看板（租户管理员）
- 展示当前租户的总文档数、向量切片总数。
- 展示当前租户近7日问答趋势、高频提问词云。
- 展示当前租户的平均响应延迟与Token消耗。

## 4. 知识库动态更新机制（多租户隔离版）

**核心原则**：所有更新操作均限定在当前租户上下文中，不同租户的数据完全隔离。

| 用户操作（当前租户） | 后端处理逻辑（同步/异步） | 向量数据库状态（带 tenant_id 过滤） | 前端反馈 |
| :--- | :--- | :--- | :--- |
| **上传新文件** | 1. 保存文件至 `/tenant-{tenant_id}/` 路径。<br>2. 启动异步任务：抽取文本 → 切片 → 生成向量，并写入 `tenant_id` 字段。<br>3. **插入**新向量至向量库（含 tenant_id）。 | 当前租户新增向量，其他租户无影响 | 提示“文件已入库”。 |
| **删除已有文件** | 1. 根据 `file_id` + `tenant_id` 删除向量。<br>2. 删除对应的原始文件。 | 当前租户移除对应向量 | 提示“文件已删除”。 |
| **覆盖同名文件** | 先删除旧向量（限定 tenant_id），再插入新向量（含 tenant_id），事务保证原子性。 | 当前租户先删后增 | 提示“文件更新成功”。 |

> **异步任务**：文件解析和向量化采用 Celery + Redis，每个任务均携带 `tenant_id`，确保处理过程隔离。

## 5. 非功能需求（质量属性）

### 5.1 性能要求
- **首字延迟**：< 500ms。
- **并发支持**：平台总并发用户数 ≥ 500，单租户内并发 ≥ 50。
- **检索速度**：向量检索 < 200ms（单租户百万级数据）。

### 5.2 安全与合规
- **多租户鉴权**：
  - 使用 **JWT** 认证，Token 中包含 `tenant_id` 和 `role`。
  - 每个 API 请求必须携带租户标识（**Subdomain** 或 **X-Tenant-ID Header**），后端中间件据此校验当前用户是否有权访问该租户。
- **数据隔离**：
  - **逻辑隔离（强制）**：所有数据库表、向量集合、Redis 键、对象存储路径均包含 `tenant_id` 字段，查询时自动加过滤条件。
  - **物理隔离（可选）**：可为大型租户提供独立数据库实例或独立向量集合（如 Milvus 的 Partition Key）。
- **权限控制**：普通用户仅能访问所属租户，租户管理员只能管理本租户，平台超级管理员可操作所有租户。

### 5.3 运维与部署
- **容器化**：所有服务支持 Docker Compose 一键启动（默认包含一个演示租户）。
- **高可用**：生产环境支持 K8s 部署，各租户可通过 Ingress 路由区分子域名。
- **日志监控**：日志中标注 `tenant_id`，便于按租户追踪问题。

## 6. 技术栈总览（多租户适配）

| 层级 | 技术选型 | 多租户适配说明 |
| :--- | :--- | :--- |
| **前端** | React + TypeScript + Tailwind CSS | 从登录页获取租户标识，并在所有请求 Header 中携带 |
| **后端框架** | Python 3.11 + FastAPI | 中间件解析租户标识，注入到请求上下文 |
| **AI 框架** | LangChain / LlamaIndex | 检索器（Retriever）增加 `tenant_id` 过滤条件 |
| **大模型** | 支持多模型（GPT / 通义 / DeepSeek） | 无租户区分，但调用日志记录 tenant_id |
| **向量数据库** | PGVector（首选）或 Milvus | PGVector 用 `tenant_id` 列过滤；Milvus 用 Partition Key |
| **关系型数据库** | PostgreSQL | 所有表含 `tenant_id` 字段，行级安全（RLS）可启用 |
| **非关系型数据库** | MongoDB | 每个文档存储 `tenant_id`，按租户索引 |
| **缓存/消息队列** | Redis | 键名前缀加 `tenant_id:`，消息队列任务携带 tenant_id |
| **对象存储** | MinIO / OSS | 路径前缀 `/tenant-{tenant_id}/` |
| **部署** | Docker / K8s | Ingress 根据子域名路由到同一后端，或由后端解析 Header |
| **反向代理** | Nginx | 可配置根据子域名转发，或统一转发后由后端识别 |
